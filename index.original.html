transaction.json
{ date: "2026-10-05",   description: "Pagamento fornecedor",   amount: 150, type: "DEBIT",   externalId: "TX001" }
amount guarda sempre o valor absoluto; type diz se é crédito ou débito. É uma convenção do domínio, não do padrão.

class OfxAdapter implements TransactionFileAdapter {   async parse(content: Buffer): Promise<Transaction[]> {     const entries = await parseOfxFile(content);     return entries.map((entry) => ({       date: normalizeOfxDate(entry.DTPOSTED),       description: entry.MEMO,       amount: Math.abs(Number(entry.TRNAMT)),       type: Number(entry.TRNAMT) < 0 ? "DEBIT" : "CREDIT",       externalId: entry.FITID,     }));   } }
DTPOSTED → date
MEMO → description
TRNAMT → amount
sinal de TRNAMT → type
FITID → externalId

Um serviço para todos os formatos
Validação, deduplicação e persistência ficam aqui, fora dos adaptadores.
transaction-import-service.ts
class TransactionImportService {   async import(     content: Buffer,     adapter: TransactionFileAdapter,   ): Promise<Transaction[]> {     const transactions = await adapter.parse(content);     this.validate(transactions);     // deduplicação, regras de negócio, persistência     return transactions;   } }
Recebe a interface, não uma classe concreta.
Por isso aceita qualquer adaptador.

O que o padrão não resolve sozinho
Duplicidades são regra do domínio
Use o FITID do OFX, mas deduplique no serviço, nunca no adaptador.
Valores
Centavos inteiros ou biblioteca decimal.
Datas
Fuso horário e formatos aceitos explícitos.
PDFs
O usuário revisa o que foi extraído.
Erros parciais
Dizer quais linhas falharam e por quê.
Segurança
Validar o conteúdo real e limitar o tamanho.
O Adapter só faz a tradução técnica.
